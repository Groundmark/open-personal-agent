# Web channel

A channel adapter ([contract](../../contracts/channel.md), channel `web`) for talking to the agent from a page on the person's phone or computer, with approvals right in the chat. Our addition alongside Signal.

**Status:** working. No runtime dependencies; the page is plain JavaScript with no libraries.

- **Pairing, mapped onto passkeys.** The account id is the person's passkey credential id and the pinned "identity key" is its public key, copied at install from the broker's `passkeys.json` (public keys aren't secrets). Signing in checks a fresh, user-verified signature by that passkey (`src/webauthn.js`, node:crypto only).
- **A password too, if the config turns it on** (`password_signin: true`; off by default), for a computer with no passkey. Whoever is in the chat can read its history and use any standing grants that are live, so it's a real way in: leave it off unless you need it. With it on, the person sets it once signed in with the passkey (scrypt, `password.json`, mode 0600); only a passkey session can set or change it, and a change signs out every other session. Ten wrong tries in 15 minutes lock it for 15 minutes. Signing in only lets the person talk to the agent; approvals still need the passkey (on a computer the browser offers "use a phone").
- **Approvals in the chat.** A message ending in an approval link becomes a card with Approve and Decline. The page runs the passkey against `/approve/<id>`, which the adapter passes to the broker's approval page (`approval_upstream`) with Host and Origin kept.
- **No history kept here,** as the contract asks: the agent's messages wait in memory until the page fetches them (server-sent events), and the page keeps its own copy on the device.
- Sessions: an HttpOnly, Secure, SameSite=Strict cookie for 30 days. Signing out also clears the device's copy of the conversation, in every open tab.
- **One-time codes** (a site's SMS or email code): with `broker_socket` set, the adapter waits on the broker for code slots (`code.slots`), and a message that is only a code while one is open goes to the broker (`code.deliver`), never to the core or the model. The core gets `[one-time code delivered]` (or that it came too late), and the chat shows a placeholder on every device; the page never saves the code. Without `broker_socket`, the broker has no slot to open for this channel, so errands that need a code can't use the web chat.
- **Catch-up after a restart:** event ids carry the run they're from, so a device that comes back after the adapter restarted gets everything it has (up to 100 messages, 24 hours) and drops what it already shows.
- **Notifications (Web Push),** with node:crypto only: VAPID (RFC 8292) and the message encrypted for the device (RFC 8291), so the push service carries it without reading it. A device gets one when the agent writes and the chat isn't in view there. A page in view says so every 20 s and says which messages it has shown; if it doesn't confirm a message within 10 s (a stream left half-open after a phone locks, say), the notification goes anyway; an approval request's notification says "Your agent needs your OK" with the summary. The server only posts to the browsers' push services (a fixed host list), never to an address a page supplies. On iPhone, notifications work once the chat is on the Home Screen.
